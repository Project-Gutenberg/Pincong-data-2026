很多人还是没明白我的意思。首先我没有说过人类比ai可靠对吧？

但是我认为，以现在ai构造证明和找bug的能力和规模，“信任”与否已经是一个需要用统计学去严肃审计的事情了。不管是用多个agent或者验证器交叉检验，还是用人力辅助审核自然语言证明，都可以降低出错的概率，但在ai大规模扫描问题、生成证明的情况下，再小的出错概率都可能被放大。

这本质上是个数据挖掘里非常基础的问题：多重假设检验。如果给你一个数据集，让你不断想各种点子来寻找规律，那么你点子想得越多、出现误报（也就是过拟合）的概率就越大。这时候你试出来的“成果”越多，对统计显著性的要求反而需要越高。

当然，我不是说非得假定AI证明黎曼猜想的概率小到可以忽略，从而一棍子打死、完全不信。我想问的是，这种概率哪怕只是定性地去估，到底该怎么估？

现实里比较靠谱的做法，就是直接看一份写得规范的自然语言证明，只要论证逻辑站得住脚，你的先验信心自然就会大大增强。而自然语言证明带来的直觉，也可以帮助我们理解题目本身的难度：这是只靠“题目看起来有多难”、或者“有多少人尝试过”没法做到的。

这本质上就是系综学习（ensembling）的思路，毕竟把完全不同路数的方法凑到一起，比用一堆高度相关的方法更能让人信服。

* * *

这事比较有趣的点在于，如果你相信ai能证明黎曼猜想这种无数人殚精竭虑思考了上百年的难题，那么为什么它就不可能找到并利用一个“许多人验证过”的编译器的隐藏bug呢？

别忘了，mythos当年最大的卖点，可就是吊打所有人的cybersecurity能力啊。

所以现在这就是个贝叶斯推断问题：两个先验假设是：1. ai证明了黎曼猜想，2. ai发现并利用了Lean编译器里某些高度非平凡的共有bug。这俩的先验概率都很低，但我们也很难“先验”地断定哪一个更低。

这就是为什么人类的理解依旧是必要的：对黎曼猜想证明的自然语言理解，对类型论的理解，对Lean验证器实现代码的理解，能帮助我们降低上述某一方的后验概率。

附带的东西很不寻常。不是一篇几十页的论文，是 14 个压缩包，239MB，解压出来 61.5GB，175,187 个 Lean 文件，1700 万行代码。Lean 是一种专门写证明的语言，写出来的每一步都能让机器逐行检查。换句话说，他交上来的不是一篇让人读的论文，是一段让机器验的程序。

这道题本身，我先用大白话讲一下它在问什么，免得后面说的检查都落不到实处。黎曼猜想是 1859 年提出来的，问的是素数的分布规律。素数就是 2、3、5、7、11 这种只能被 1 和自己整除的数，它们在数轴上的分布看起来乱糟糟的，但黎曼猜想说，背后有一条整齐的线：一个叫 zeta 函数的东西，它所有非平凡零点的实部都是二分之一。如果这条线成立，素数的分布就有了规律可循。这道题挂了 167 年，Clay 研究所悬赏 100 万美元，多少数学家一辈子扑在上面，连边都没摸到。

消息出来不到一天，验证那边就动起来了。MIT 的计算数论学家 Sutherland 在自己的机器上把整套东西重跑了一遍，还开了个实时更新的验证页。结果是这样的：175,187 个 Lean 模块，全部编译通过，零错误。Lean 内核检查，也就是最核心的那道关，175,187 个全过，一个没被拒。独立的 nanoda 检查器，一个用 Rust 写的、跟 Lean 完全独立的检查程序，也点头了。还有一个叫 con-leche 的检查器，验证了 146 万多条声明，同样通过。

更关键的是公理。Lean 有个命令能查一个证明到底依赖了哪些假设，结果显示，这五个核心定理只用了 Lean 的三条标准公理，没加任何新公理。没走后门，没偷藏假设。Sutherland 自己在验证页上写了一句大白话：代码已经编译过、被 Lean 内核独立复核过，只用了三条标准公理，“老实说，出问题的概率大约是零”。

牛津的 Maynard 也表态了。他是菲尔兹奖得主，专门研究素数的，对《纽约时报》说，他觉得这个证明“极有可能正确”，把握在 98%–99%。这个数很有分量：Maynard 不是在客套，他是在说，以他的专业判断，这套东西大概率是对的。

说到这儿，很多人会问：那不就是证出来了吗？还差什么？差的东西，恰恰是最值得讲清楚的部分。

第一道没过的关，是比对检查。Lean 文件能编译、能通过检查，证明的是“这个形式化的命题成立”。但形式化的命题和数学家脑子里的黎曼猜想之间，还得对上号。万一形式化的时候哪里写岔了，机器验的就不是原来那道题。数学家 Elliot Glazer 看过形式化的命题，说它确实是广义黎曼猜想，但完整的比对检查，到 11 月 21 号上午还在跑。这道关不过，“已证明”三个字就写不上去。

第二道没过的关，是人还没读懂。1700 万行代码，没有任何一个人能从头读到尾。数学家们现在的工作，是去理解这套论证到底是怎么走通的，这需要时间。机器说“对”，和人说“我懂了为什么对”，是两回事。数学界要的，不只是对，还要懂。

第三道没过的关，是 Clay 研究所的流程。黎曼猜想仍然列为“未解决”。百万美元奖金按规矩来：发表、被数学界广泛接受、再经过两年的审查期。一天之内，这些都不可能走完。所以你现在看到任何标题写“黎曼猜想已被证明”，都可以直接判定为标题党。

这三道关没过，不代表这事不厉害。恰恰相反，我觉得它厉害的地方，正在于验证流程本身被重构了。

以前验证一个数学证明，靠的是同行评议：几个人花几个月甚至几年，把论文从头读到尾，挑错、质疑、来回拉扯。这次不一样：证明先以代码的形式交出来，机器先验一遍，验的是“每一步推导合不合规矩”，而不是“这个思路漂不漂亮”。机器验完，人再慢慢消化思路。顺序倒过来了：先过机器关，再过人脑关。

这种变化意味着什么？意味着以后越来越多的大证明，可能会先以代码的形式出现，再慢慢被人消化。1700 万行代码的证明，靠一个人是写不出来的，也读不完。AI 出现之前，这种规模的论证根本没法组织起来。现在机器能搭脚手架，人负责把方向、做判断，分工变了。

我还想多说一句 Alpöge 这个人的位置，因为这决定了这事的性质。他是 Anthropic 的数学家，哈佛的初级研究员，不是那种躲在象牙塔里十年磨一剑的传统形象。他和 Claude 的合作持续了几个月，最后 41 天冲刺。这说明什么？说明 AI 在数学里的角色，已经从“帮你算个数”变成了“跟你一起想”。这不是一个工具在执行指令，是一个合作者在参与论证。

当然，冷水也得泼。历史上有过教训：看着像证出来了，最后发现形式化写岔了，或者关键一步藏了个没人注意的假设。98%–99% 的把握，剩下的那 1%–2%，就是数学较真儿的地方。Maynard 自己也说了，计算机验证还得仔细过一遍。专业人士的谨慎，恰恰是这事可信的原因：没人急着盖章，所有人都在等比对检查跑完、等更多人读懂。

对普通人来说，这事有三个看点。第一个看点是 AI 干活的方式变了：以前是聊天、写稿、画图、写代码，现在开始啃数学里最硬的骨头了。第二个看点是验证的方式变了：机器先验，人再消化，证明的形态本身在变。第三个看点是门槛在变：以前一个大证明靠几个天才，现在靠人和机器的分工，规模的天花板被顶高了。

最后收个尾。评价这件事，别只看“证出来了没有”，要看三样东西：机器验没验过、人读没读懂、流程走没走完。现在第一样过了，第二样刚开始，第三样还早。这三样都走完，才是真正的盖章。167 年的题，走到今天这一步，已经够写进历史了。至于最后那道手续，让子弹再飞一会儿。

再补一句概率怎么理解。98%–99% 不是说证明已经对了 98%，而是 Maynard 这种专业判断下的信心。剩下的 1%–2% 里，装的是形式化写岔、检查器共有的盲区，还有人没读懂的部分。概率高，不等于手续走完了，数学要的是没有漏洞，不是大概率没有漏洞。

接下来我会盯着三件事。比对检查跑完没有，独立的复现是不是还在继续，有没有人把这 1700 万行代码讲成普通人能跟上的论证。这三件事里任何一件出结果，都会改变上面说的判断。在那之前，我的看法不变：机器验过的部分值得认真对待，人还没读懂的部分，同样值得认真对待。

还有一个容易被忽略的细节。Lean 证明里那五个核心定理只用了三条标准公理，这个结果本身就很干净。如果中间藏了新假设，检查器会直接把依赖列出来。现在依赖是干净的，剩下的疑问就集中在形式化的命题到底是不是黎曼猜想。这也是为什么比对检查这么关键，它回答的不是代码对不对，而是代码证的是不是这道题。

有些小红书用户说自己用豆包或DeepSeek有时候会推理出错，借此来攻击这个证明不靠谱。

这里用一个简单的小例子：素数有无穷多个，来介绍下 Lean 的证明原理。

**整体的原理**

说人话版：从公理和已证定理出发，把每一步“因为xxx，所以yyy”写成 Lean 代码，编译通过就说明这一步正确。最后只要结论是黎曼猜想就行了。

当然这么说还是有点问题的，准确地说是写的一系列策略，最终会生成一个证明项。

Lean 的一个极小内核会检查这个证明项的类型，是否恰好是你要证明的命题。

策略只是给人写证明用的脚手架，证明项才是内核真正检查的对象。

可以从最小的例子开始理解。

**等式的传递性**

先看 Lean 4 里最基础的证明：

```
example (a b c : Nat) (h₁ : a = b) (h₂ : b = c) : a = c := by
  rw [h₁]
  exact h₂
```

*   example：这是一个演示，不需要命名。
*   (a b c : Nat)：声明三个自然数。
*   (h₁ : a = b) (h₂ : b = c)：两个已知条件。
*   : a = c：要证明的目标。
*   by：进入证明模式，后面写策略。

一步步推理体现在哪？

在 Lean 编辑器（比如 VS Code + Lean 插件）里，光标每移动一行，右侧会显示目标状态的变化。

初始状态：

> h₁ : a = b  
> h₂ : b = c  
> ⊢ a = c

执行 rw \[h₁\] 后：

> h₁ : a = b  
> h₂ : b = c  
> ⊢ b = c

rw \[h₁\] 的意思是重写：利用 h₁ : a = b，把目标里的 a 替换成 b。目标从 a = c 变成了 b = c。

执行 exact h₂ 后：

> All goals completed.

exact h₂ 的意思是：当前目标 b = c 恰好就是已知条件 h₂，直接引用它，证明完成。

这就是一步步推理最直观的体现，每一行策略都在改变待证目标，直到目标被关闭。

**Lean内核的证明项**

rw 和 exact 是给人用的策略。它们执行完后，Lean 会在底层生成一个证明项。上面这个例子的证明项大致相当于：

> Eq.trans h₁ h₂

意思是：利用等式的传递性，从 h₁ : a = b 和 h₂ : b = c 推出 a = c。

内核检查的是这个证明项：

> Eq.trans h₁ h₂ 的类型是不是 a = c？

如果是，证明通过。

所以一步步推理有两层：

*   人类可读层是by 后面的策略序列，目标状态一步步变化。
*   机器检查层是策略生成的证明项，每个节点对应一次推理规则。

**现在把例子放大一点。我们要形式化一个经典定理素数无穷多**

> 定理：素数有无穷多个。  
> 等价表述：对任意自然数 n，存在素数 p，使得 p ≥ n。

假设项目叫 MiniPrime，文件树如下：

> MiniPrime/  
> ├── Basic.lean -- 定义素数、最小质因子等基础概念  
> ├── Factorial.lean -- 证明 n! + 1 > 1 等阶乘引理  
> ├── MinFac.lean -- 证明最小质因子的性质  
> └── Infinite.lean -- 主定理：素数无穷多

这四个 .lean 文件，就是四个模块。

模块 Basic.lean：定义和基础接口

```
-- MiniPrime/Basic.lean
module

/-- 一个数 p 是素数：p > 1，且任何因子都只能是 1 或 p。 -/
def IsPrime (p : Nat) : Prop :=
  p > 1 ∧ ∀ d, d ∣ p → d = 1 ∨ d = p

/-- 最小质因子，这里只声明接口。 -/
def minFac (n : Nat) : Nat := ...

/-- 公开一个基础引理：n! + 1 > 1。 -/
public theorem factorial_add_one_gt_one (n : Nat) : n ! + 1 > 1 := by
  ...
```

这个模块的职责是：定义概念，提供后面模块要用的接口。它编译后生成 Basic.olean。

模块 MinFac.lean：证明一个关键引理

```
-- MiniPrime/MinFac.lean
module

import MiniPrime.Basic

/-- 关键引理：若 n > 1，则 minFac n 是素数，且整除 n。 -/
public theorem minFac_prime_and_dvd (n : Nat) (h : n > 1) :
    IsPrime (minFac n) ∧ minFac n ∣ n := by
  ...
```

开头 import MiniPrime.Basic 的意思是：需要 Basic 模块里已经定义好的 IsPrime、minFac 等接口。

但它不重新证明 Basic 里的东西。编译时，Lean 会加载已经检查过的 Basic.olean，把其中的声明当作可用环境。MinFac.lean 自己编译成 MinFac.olean。

这个模块内部有它自己的一步步推理，用来证明 minFac\_prime\_and\_dvd。

但对外，它只暴露这个定理的类型，不暴露证明细节。

模块 Infinite.lean：主定理

```
-- MiniPrime/Infinite.lean
module

import MiniPrime.Basic
import MiniPrime.Factorial
import MiniPrime.MinFac

/-- 主定理：对任意 n，存在素数 p ≥ n。 -/
public theorem exists_infinite_primes (n : Nat) :
    ∃ p, n ≤ p ∧ IsPrime p := by
  let N := n ! + 1
  have hN : N > 1 := factorial_add_one_gt_one n
  have hmin : IsPrime (minFac N) ∧ minFac N ∣ N :=
    minFac_prime_and_dvd N hN
  have hgt : minFac N > n := by
    ...
  exact ⟨minFac N, Nat.le_of_lt hgt, hmin.1⟩
```

这里

1.  令 N = n! + 1；
2.  由 Factorial 模块的引理得到 N > 1；
3.  由 MinFac 模块的引理得到 minFac N 是素数且整除 N；
4.  证明 minFac N > n；
5.  取 p = minFac N，组装出 ∃ p, n ≤ p ∧ IsPrime p。

每一步都是一个 have，都引入一个新的中间结论。编辑器里同样能看到目标逐步被拆解和填补。

**模块的作用**

模块不替代逐步推理，而是把许多个逐步推理分装到不同文件里。

Basic.lean 内部有它自己的逐步推理，证明 factorial\_add\_one\_gt\_one；

MinFac.lean 内部有它自己的逐步推理，证明 minFac\_prime\_and\_dvd；

Infinite.lean 内部有主定理的逐步推理，但它把前两个模块的定理当作已知结论来用。

所以：每个模块内部都有一步步推理。模块之间通过引用已证定理连接，而不是把对方的证明细节重新展开。

**Lean内核检查**

Lean 的内核检查粒度是单个模块，不是整个项目。检查可以按依赖顺序进行：

1.  检查 Basic.olean：确认 IsPrime 定义合法、factorial\_add\_one\_gt\_one 的证明项类型正确。
2.  检查 Factorial.olean：它依赖 Basic，内核加载已检查的 Basic 环境，检查 Factorial 自己的证明项。
3.  检查 MinFac.olean：同理，依赖 Basic。
4.  检查 Infinite.olean：加载前面已检查的 .olean，检查主定理的证明项，确认它的类型正好是：

```
∀ n : Nat, ∃ p, n ≤ p ∧ IsPrime p
```

检查完一个模块，释放内存，再处理下一个。

**黎曼猜想**

黎曼猜想的 1700 万行代码，被拆成 17 万多个模块。每个模块只依赖它 import 的模块，编译成一个 .olean。内核或独立检查器按依赖顺序逐个回放检查。

主定理模块 Riemann.Main 的证明项只负责调用前面模块公开的接口，最后让内核确认：这个证明项的类型 = RiemannHypothesis。

Lean 小内核保证证明项通过内核类型检查，推导无懈可击。

我们解压检索了全部 175,187 个 Lean 文件，梳理主依赖树、核对核心定理的类型签名。核查结论：从形式结构上，没有发现偷换命题、隐藏约束这类逻辑陷阱；多内核机器验证的结果相当扎实；但对论证本身的数学语义核验几乎还没有启动，整套证明的命门落在一个尚无公开回应的关键节点上。

下面把我们拆出来的东西一件件摆。

一、黎曼猜想到底在猜什么
------------

先把问题界定清楚。后面所有判断都挂在上面。

1859 年，黎曼在一篇八页的论文里写下了 zeta 函数，做了解析延拓，然后说了一句大意是：所有非平凡零点的实部似乎都等于 1/2。注意他的措辞——"似乎"。他没有说"我证明了"，他说"看起来是这样"。他甚至说这"极有可能"但"还没严格验证"。

黎曼在猜什么？他计算了前几个零点，发现都在 1/2 上，他觉得可能全都在。这是一个归纳猜测——从有限观察推断普遍规律。

一百六十多年过去了，计算机验了约十万亿个零点，全在 1/2 上，没有一个反例。但有限数值验证永远不能替代对全部无穷多零点的严格证明。这件事本身不构成疑难——疑难在于"为什么全都落在 1/2"。

1/2 这个数字太特殊了。它不是 0.49，不是 0.51，不是任何近似值——恰好是对称中心。就像你扔了约十万亿次硬币，每一次都恰好竖着站起来——你知道这不是巧合，但你不知道是什么机制让它每次都竖着。

数学家要的不是"约十万亿次都竖着"——这个事实早就有了。要的是"它为什么只能竖着"。

学界内部对"黎曼猜想要证什么"的回答，实际上分三层：

Claude 的证明回答的是命题层面——证零点在 1/2。没有回答纲领层面，也没有回答接受度层面。这个区分后面会用到：命题层面、纲领层面、接受度层面，是三件不同的事。

二、证明的真实结构——约 1737 万行证前提，一段反射逻辑收口
--------------------------------

截至我们检索时，没有看到公开的内部结构拆解。我们拆了，拆到了代码级别。

主链入口在 Main.lean。从这里出发，依赖树是这样的：

*   Main.lean 调用 Formalism.VW.rh\_of\_every
*   rh\_of\_every 调用 Formalism.VW.rh\_of\_right
*   rh\_of\_right 的前提参数叫 hz

hz 的完整签名，一字不差地从代码里抄出来：

```
hz : forall s : C, 1/2 < s.re -> s != 1 -> riemannZeta s != 0
```

翻译成大白话：对所有复数 s，只要 s 的实部大于 1/2 且 s 不等于 1，zeta 函数在 s 处就不等于零。这就是"右半平面无零点"。

整个证明约 1737 万行代码，全部在证这一件事。175,187 个文件，围绕的全是这一个前提。

那收口呢？hz 成立之后，怎么推出零点在 1/2 上？几十行，用的是函数方程。

先纠正一个常见误写：干净的对称性不是 zeta(s) = zeta(1-s)——裸的 zeta 不等于它自己的反射，代一个数就不成立（zeta(2) = pi²/6，zeta(-1) = -1/12）。真正对称的是补上 Gamma 与 pi 因子之后的完成函数：

```
Lambda(s) = pi^(-s/2) × Gamma(s/2) × zeta(s)
```

它满足 Lambda(s) = Lambda(1-s)，对称轴正是 Re(s) = 1/2。

代码里用的 riemannZeta\_one\_sub 就是这条函数方程的 Lean 版本：

```
zeta(1-s) = 2 × (2×pi)^(-s) × Gamma(s) × cos(pi×s/2) × zeta(s)
```

带着 Gamma 和 cos 修正因子。收口要的只是它的一个推论：在关键带内这些因子非零，于是 zeta(s0) = 0 当且仅当 zeta(1-s0) = 0，零点关于 1/2 对称。

这是 1859 年黎曼自己推导的函数方程，一百六十七年无争议。

收口逻辑是反证法加对称反射，三步：

1.  假设存在一个非平凡零点 s0，其实部 sigma 不等于 1/2。
2.  三分法——要么 sigma > 1/2，要么 sigma < 1/2。
3.  如果 sigma > 1/2，那 s0 就在右半平面——但 hz 说了右半平面无零点，矛盾。如果 sigma < 1/2，用上面那条函数方程（靠完成函数的对称性）反射到 1-s0，则 1-s0 的实部 > 1/2——又落在右半平面，又跟 hz 矛盾。

三个方向都堵死了，只剩 sigma = 1/2。

1/2 不是算出来的——是函数方程的对称中心。把所有其他位置排空之后，零点只能落在对称轴上。

这就是整个证明的结构：约 1737 万行证前提，几十行用对称性收口。在 Mathlib 既定定义与已知定理的前提下，这段收口逻辑是自洽的：函数方程、反证法、三分法、零点对称反射这一套推理，不存在明显逻辑跳步。

那命门在哪？在约 1737 万行的前提里。

四、remark 与代码的系统性错位
------------------

Alpöge 放出的 remark.pdf 只有四页，是整个证明唯一的人类可读说明。所有人都在拿这四页当路线图——媒体拿它写新闻，数学家拿它判断方向。

我们全库检索了 175,187 个文件，把 remark 里提到的四个关键词逐字 grep。结果：

*   remark 说 Vandiver（第 17 条"fight for a significant weakening of Vandiver"）——代码 0 命中。整个 175,187 个文件里没有 Vandiver 这个词。取而代之，代码走的是 Herbrand 群论恒等式加几何实现，把 Vandiver 那一环消化掉了或绕开了。
*   remark 说 Bost slope inequality（第 13 条）——代码 0 命中。若干匹配全是文件名子串巧合，没有实质引用。取而代之，代码用的是本项目自证的斜率界。
*   remark 说 mimicking multiplicity（描述核心方法）——代码 0 命中。mimicking 这个词在代码里不存在。取而代之，代码走的是 theta 提升、Galois 表示、模性提升的自守链，不是"模拟重数"的叙事。
*   remark 说 2/3 链长门槛（第 14 条"stop at 2/3 a priori"）——代码 0 命中。代码里 104 处 2/3 全是分析常数，没有一处是"链长门槛"。取而代之，链长的控制跟 2/3 无关。

四个关键词，四个零命中。这不是我们解读的——是逐字 grep 175,187 个文件的事实。

作者自己说了几句话。他在 remark 里写："部分时间线是转述 Claude 的 slop 摘要，might make zero sense。"他在公开声明里说："presenting the world with a complete argument before having mastered a massive neighbourhood around its mathematics。"他还说："may have baked lots of strange suboptimal choices into the argument。"

翻译过来：作者自己承认，他对证明的描述可能跟证明本身对不上。

但这不属于刻意造假：remark 只是一份非正式思路摘要，它描述的路线，和最终形式代码落地的论证路径发生了偏离。失真的后果是：如果数学界拿 remark 当审查路线图，会浪费时间在不存在的东西上。真正的命门——theta 提升链里的 automorphy-lifting 节点——反而不在 remark 的视野里。

五、对称性的两层来源
----------

整个证明的因果链，拆到底是一条线：对称性进来 → 右半平面无零点 → 反射 → 零点在 1/2。

但对称性本身有两层来源，而且没有显式统一。

顶层：Mathlib 函数方程（完成函数层面）。Lambda(s) = Lambda(1-s)——代码里对应 riemannZeta\_one\_sub（带 Gamma/cos 因子）和 completedLFunction\_one\_sub 的完成形式，1859 年黎曼给的，一百六十七年无争议。这是收口那一步的数学基础。注意对称的是完成函数 Lambda，不是裸 zeta：裸 zeta(s) 不等于 zeta(1-s)。

底层：本项目自证的 Howe 对偶 / Gelfand-Kazhdan 对偶。约 1737 万行的 theta 提升链里，每做一次 theta lift，依赖的是酉群之间的 Howe 对应。这个对偶性不是 Mathlib 引用——是本项目自己证的 theorem。

两层对称性，一个来自 1859 年的已知定理，一个来自 2026 年的新代码。它们在数学上是相关的——Howe 对偶是更一般的自守对称性，函数方程是它在 zeta 函数上的投影——但代码里没有一条定理把两层显式接起来。

这意味着什么？意味着整个证明的真实因果链是：用一种对称性（Howe 对偶）证了右半平面无零点，然后用另一种对称性（完成函数的函数方程）做反射收口。进来的是对称性，出去的是对称性的对称轴（临界线）。

这个结构本身不算错——两层对称性在数学上确实相关。但它引出一个问题：如果约 1737 万行的 Howe 对偶那一层有任何瑕疵，顶层的函数方程救不了它。函数方程只管收口，不管前提。前提的全部重量压在 Howe 对偶和 theta 提升链上。

那 theta 提升链可靠吗？

那问题出在哪？

七、命门——automorphy-lifting 那扇门
----------------------------

约 1737 万行的 theta 提升链里，有一个节点叫 automorphy-lifting。

theta 提升每做一次，会造出一个 Galois 表示。这个 Galois 表示必须满足"自守性"——就是说它必须对应一个自守形式。automorphy-lifting 是"证明某个 Galois 表示是自守的"这一步。这是朗兰兹纲领里极其精密的工具，依赖大量深层数论条件。

Birkbeck（UEA 自守形式专家）在社区 Zulip 上指出：一个关键 bound 依赖 automorphy-lifting argument。需要明确：这是社区线上讨论的观点，不是正式书面审稿意见，没有经过成文论证；来源为社区讨论和 TechCrunch 转述，尚未以正式论文或预印本形式发表。它指向的是数学逻辑层面而非编译层面的问题，具体细节仍需等待相关专家的正式表述。

反过来，也没有人证明这个自守提升不可能成立——目前是悬置、待核验，不是已否定。

但如果这一步没走通——某个 Galois 表示的自守性没有被严格证明——那整条 theta 提升链就断在中间。链断了，"右半平面无零点"就没证出来，几十行收口就没东西可收口。

这就是命门。不在收口那几十行——收口逻辑自洽。不在前提的全域性——全域，没有楼层问题。不在编译器——六项过了。不在 sorry 或 axiom——全库扫描为零。

命门在约 1737 万行的桥中间，一个叫 automorphy-lifting 的节点上。Birkbeck 说这个节点可能没接上。截至目前，未见公开回应。

这个判断和我们拆解的结构完全吻合：风险落在前提链内部，而非收口逻辑。约 1737 万行证前提，前提的桥中间有一个节点可能没接上，而那个节点恰好是整个证明最硬的数学——高秩自守形式、Galois 表示的模性提升，作者自己说"在这一领域 Claude 的技术能力令他惊叹"但"自己掌握有限"。

八、另外两个值得知道的
-----------

Masullo 同日人类声明。就在 Alpöge 放出代码的同一天，美国数学学会主席 Ravi Vakil 披露：斯坦福大学博士后 Alessandro Masullo 数月前可能已经独立完成了一份没有 AI 参与的广义黎曼猜想证明，约 940 页，Brian Conrad 已花费数月审阅、反馈正在整合。但 Masullo 底稿同样未经正式同行评审发表。两边都是待验收状态——不要因为有人类版本就认为 AI 只是重复，也不要因为 AI 有 Lean 代码就认为人类版本多余。

作者自述未完全理解。Alpöge 在 remark 里坦白：高秩自守形式那几段，Claude 在推，他自己在跟进但承认'可能完全说不通'，一切以 Lean 代码为准。在传统单人纸笔证明的范式里，作者通常吃透全部论证——Perelman 理解自己的证明，Wiles 理解自己的证明。但这种 AI 协同的巨型形式化证明是全新范式，出现"作者还没完全吃透整套论证"的局面是新范式带来的特殊难题，不是作者能力不足。这意味着同行评审的难度大幅上升——你不是在审一个作者理解了的东西，你是在审一个作者自己都还在消化的东西。

先说结论：这次验证的可信度很高，但「为真」和「被认证解决」是两件事——问题里那句「多大概率为真」，答案得拆成两层。

先交代我为什么会认真看。

这题被"证明"过很多回了。2018 年阿蒂亚在海德堡那场，台上说证出来了，全场鼓掌，第二天漏洞就被人翻出来。今年 8 月还有人从物理模型绕进来，也宣布证出来了。所以 11 月 20 日晚上看到消息，我第一反应是：又来。

机器这头办完了。我想弄明白另一头：人类自己，一百六十七年，走到哪儿了。要讲这个，得先把题说清楚。

素数就是 2、3、5、7、11 这些，除了 1 和自己谁也除不尽。你大概也发现过：越往后越稀。

稀到什么程度？一百以内 25 个，平均 4 个数一个；一千以内 168 个；到一百万，13 个里才出一个。

稀归稀，它不乱。十九世纪高斯发现，这些疏密落在一根平均线附近，而这根线能算。

麻烦就在"平均"两个字。真实情况是围着这根线上下抖，抖多少，高斯算不出来。好比你知道全班平均分八十，猜不出下一个进门的人考几分。

1859 年，黎曼换了个问法：不看素数了，改看一个函数，后来叫 ζ 函数（念"泽塔"）。

函数在某些位置算出来正好是零，这些位置叫零点。

黎曼发现的事很邪门：素数抖成什么样，全看这些零点站在哪儿。

素数像一段鼓点，听着没谱。黎曼发现它其实是很多音叉同时响出来的，一个零点一支音叉——音叉站在哪儿，鼓点就敲成什么样。所以数学家管这个叫"素数的音乐"，不是修辞，是字面意思。

音叉站哪儿得用两个数标，像经纬度。黎曼算了前几支，发现"经度"全是 0.5。于是他猜：剩下的也都在这条线上。

这就是黎曼猜想，一句话——这个函数有一大堆零点，除了几个明摆着的，剩下的经度全在 0.5 那条竖线上。

为这一句话，文献里一千多条定理都得先"假设它对"。它一倒，全悬空。

![](data:image/svg+xml;utf8,<svg xmlns='http://www.w3.org/2000/svg' width='1200' height='675'></svg>)

这里我要多说一句，因为很多人把它理解成"数学家的自娱自乐"。不是。素数分布一旦被彻底锁死，跟素数有关的估算全都能收紧，包括今天你手机里那些加密算法所依赖的"大数不好拆"。当然这不意味着明天密码就破了，别被标题吓着——它影响的是长期的理论边界，不是今晚。

接下来是这一百六十七年。

1896 年，阿达马和德拉瓦莱普桑证出素数定理。这不是黎曼猜想，是绕路——只要证出 ζ 在经度 1 那条线上没零点就够了，1 在 0.5 右边，好证得多。

这动作后来重复了无数次：不证"全在 0.5"，只证"越来越靠近"。

1914 年，哈代证出线上有无穷多个零点。你可能觉得这算什么进展——在那之前，连"有没有"都没人知道。

然后就慢了。1942 年塞尔伯格算出"有正的、很小的比例"；1974 年莱文森过三分之一；1989 年康瑞过五分之二；2020 年是十二分之五。

换个说法你就知道多慢：一百个零点，1974 年能保证 33 个在线，2020 年能保证 41 个。四十六年，多认了 8 个。剩下 59 个，不知道在哪儿。

还有一路是硬数。2021 年 Platt 和 Trudgian 用区间算术，严格证到 3×10¹² 高度以下的零点全在线上。之前流传的"十万亿个"没发表、没人复现，浮点算的，误差没界定，不算证据。

十二万亿个，听着很多。可十二万亿除以无穷，还是零。

有限到无穷这道坎，一百六十七年，一次都没跨过去。

0.875，不是 0.5。前者允许零点撒在 0.5 右边一整片区域；后者要求它们精确站在 0.5 那条线上。

一、它证的还是不是原来那道题。0.5 换成 0.875，"无外力"换成"带外力"，都是缩水。缩得还挺有道理，可性质变了。

二、有没有人独立跑过。机器验过不算，得人验。

这两条都不难用，难的是愿意用。热搜挂出来的时候，多数人只看标题里有没有"解决"两个字。

说回这次。

第一条它过了：证的确实是黎曼猜想本身，不是缩水版。

第二条过了一半。机器侧几十人独立复现了，人侧还没有。

所以克雷那边一个字没改。规矩是论文正式发表，再挨满两年挑刺。这个章盖的是"这段代码证的这句话是对的"，不是"这道题结了"。

### Lean 的“通过”证明了什么，没有证明什么：三个结构性缺口

形式化验证在数学哲学中有一个已被清晰刻画的限度。村山文隆在专门讨论 AI + Lean 范式的论文中，区分了三个无法被 Lean Kernel 弥合的缺口：

**第一，形式化缺口。** 把一个自然语言表述的数学问题翻译成 Lean 陈述，本身就是一个**解释性行动**，其正确性处在证明助手的作用范围之外。Lean 能确认“从这个形式陈述到这个形式证明的推导是合法的”，但它不能确认“这个形式陈述忠实地捕捉了数学家原本想问的那个问题”。所谓“五个核心定理只依赖三个标准公理”，恰恰掩盖了更根本的问题：**那五个形式陈述是不是黎曼猜想、是不是某个千禧年问题，是由人——而不是 Lean——来判断的。**

**第二，哥德尔极限。** Lean 底层的形式系统无法自证一致性，因此“经过 Lean 验证”并不携带绝对的认知保证。这不是技术细节，而是说：形式验证的权威是**系统内部的**，它无法从外部为整个系统本身背书。

**第三，理解缺口——这是最关键的。** 机械的类型检查是一种**句法操作**：它确认符号串在规则下是良构的，但它**不携带任何语义理解**。一个 1700 万行的 Lean 证明通过了检查，只意味着它在 CIC 系统中没有类型错误；它**不意味着有任何心灵理解了它“为什么”成立**。

格洛滕迪克的工作方式与“解题—验证”范式是**方向相反的**。数学界历来不乏以破解难题为路径的顶尖高手，但格洛滕迪克“感兴趣的研究对象并非难题，而是那些看上去会指向更大而又隐藏着的结构”——他的目标是“发现和创造问题的自然栖息之家”。他的“ rising sea ”方法不是正面攻克一个命题，而是**提升抽象层次，直到原本像山一样的问题变成岛屿**。这是一种**创造概念框架**的活动，而不是在给定框架内搜索证明。

更关键的是他对“虚空”的体验。格洛滕迪克所描述的深度，不是在既有形式系统中“向下挖”，而是在抽象化到某个临界点之后，发现**门后不是房间，而是深渊；深渊不是黑暗的虚空，而是每一层都更丰富的结构，没有底**。这种经验——**在创造新框架的过程中被一个尚未被命名的结构抓住**——不可能被还原为“在 Lean 中搜索一个类型正确的项”。算法只能在**已经被给出的形式空间**中搜索；格洛滕迪克式的活动是**创造那个空间本身**。

我想格洛滕迪克会提醒他：

**数学最深刻的部分恰恰发生在可靠性问题被提出之前——发生在你决定什么值得证明、用什么概念去重新描述整个领域的时候。**

**再多说两句**

“25 万页证明难道真的人去看和理解？”——这是一个假二分：要么人逐页读完全部形式化代码，要么只能让 AI 解读 AI。

但数学理解从来不是按页数吞吐。

人读论文也不读 LaTeX 的每个 token，不逐条检查编译器的每条指令。人类理解数学靠的是**压缩**：抓住定义、关键引理、证明架构、不变量、归约路径、模块接口。

形式化证明恰恰可以模块化

人类可以审查定理陈述是否忠实、接口是否合理、关键引理是否可信、独立检查器是否独立、复现是否一致。

25 万页 Lean 代码里大量是库定义、重复结构、自动化脚本和类型标注，不等于 25 万页“必须逐行领悟的数学思想”。

把“不能逐行读”说成“人类理解无意义”，是把**阅读负担**偷换成**理解不可能**。
